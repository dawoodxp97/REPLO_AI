# Archify integration plan

Status: proposal (9 Nov 2026). Nothing is built yet.
Source studied: [tt-a1i/archify](https://github.com/tt-a1i/archify) at `11b0d60` (v3.2.0).

## 1. What archify is

- **An agent skill, not a library or a service.** An agent such as Claude Code, Codex or Cursor writes typed JSON for one of 10 diagram types, or a Markdown "explainer" page. Archify's Node CLI then validates it, lays it out and writes one standalone HTML file. Each file carries a 787 KB template with a built-in viewer.
- **No LLM and no code analysis of its own.** The agent reads the repository. Archify only checks that each cited file and line range exists at a pinned commit.
- **Its renderers are CLI scripts.** They use top-level `await`, read `argv` and write files. Even archify's own explainer runs them as child processes. There is no API we could import.
- **Licences.** The code is Apache-2.0, with an older MIT grant. Some bundled brand icons carry their own licences: Jenkins and Rust are CC-BY-SA, and Vue is CC-BY-NC-SA. Explainer charts use vendored Pele (MIT).

## 2. Three ways to use it

| Way | What it means | What we get | What it costs | Verdict |
|---|---|---|---|---|
| **1. Embed** | Vendor archify at a pinned commit. The worker runs its CLI for each diagram, and the product shows the HTML in a sandboxed iframe on a separate origin. | Every viewer feature on day one | <ul><li>A second design system beside `DESIGN.md`</li><li>About 0.8 MB per diagram</li><li>A Node subprocess per diagram on the VPS worker</li><li>A separate origin for the CSP</li><li>Our axe and touch-size gates would scan markup we don't own</li><li>Brand marks must be stripped</li><li>Its browser gate needs Chrome</li></ul> | Not recommended as the main path |
| **2. Native port** | Adopt archify's typed diagram shapes, checks and viewer ideas, built in Replo's stack: <ul><li>Zod contracts</li><li>Grounding in the API</li><li>Mermaid generated by the system</li><li>A React interaction layer that uses our tokens</li></ul> | <ul><li>Every feature that fits our rules</li><li>One design system</li><li>Our existing CSP, accessibility and test gates</li><li>Grounding stays "the model points, the system quotes"</li></ul> | More build work | **Recommended** |
| **3. Interop export** | "Download as archify JSON". This exports a tutorial diagram in archify's format: the repository URL, the commit, and each file and line range. Anyone with the archify skill can then open it in archify's full viewer. | Archify's own viewer for power users, at almost no cost | Owner-only for private repositories | **Add on top of way 2** (phase E) |

## 5. Risks

- **Stored tutorials.** They keep content schema v1. The read path upcasts them, and `CONTENT_SCHEMA_VERSION` moves to 2.
- **Token cost.**
  - Every diagram the model writes adds output tokens on the user's own key, within the budget guard.
  - Diagrams built by the system cost nothing.
- **Hooking interactions onto Mermaid.** Mermaid's SVG element IDs must be stable enough for each diagram type. Phase C includes a spike to check this before phase D. If the IDs aren't stable, those types get our own SVG renderer.
- **No-JavaScript readers.** Mermaid 12 renders in the browser only, so the text alternative is what serves readers without JavaScript.
- **Keyboard shortcuts.**
  - Diagram shortcuts apply only while a diagram has focus.
  - This keeps them from clashing with the player's own shortcuts, such as `r` for references.
- **Free models.**
  - Free models may struggle with the richer JSON.
  - The lite pipeline keeps workflow diagrams only.

## 6. Decisions needed

1. **Approach.** The recommendation is the native port plus the archify JSON export. The alternative is to embed archify's HTML.
2. **Non-goal.** Should "interactive dependency graph" be narrowed so that phase D can go ahead?
3. **Dropped features.** Do you agree to drop the waterfall, panel patching and per-panel follow-ups, since each conflicts with a rule?
4. **Order.** Start with phase A, then B and C, then D to H in any order.
