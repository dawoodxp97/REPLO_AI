# ADR-010 — Everything on Cloudflare: Workers, Workflows, Neon + Hyperdrive, R2

- **Status:** Accepted (2026-11-18, plans R9). Supersedes ADR-002's pg-boss delivery choice and the VPS hosting decision (blueprint §17.3, §11). See MEM D-128.
- **Context:** R9 must deploy the whole product. The 2026 Workers runtime ships Node.js compatibility by default (compatibility date ≥ 2026-08-04; `node:crypto`, `node:buffer`, `node:stream`, `node:net`, `node:fs` in-memory, 64 MiB bundles), Fastify runs behind `cloudflare:node`'s `httpServerHandler`, `@opennextjs/cloudflare` is the mature production path for Next.js 16 on Workers, and Hyperdrive is the documented way to reach external Postgres with `pg`/Drizzle. Cloudflare Workflows (durable multi-step execution with persisted state, retries, no overall timeout) matches the pipeline's already-checkpointed stage model almost 1:1. The prior plan (one VPS with Docker Compose + Caddy, pg-boss, self-hosted Postgres) costs a fixed ~€6–7/mo but keeps a server to patch, back up and drill restores on.
- **Decision:** Host everything on Cloudflare and let GitHub Actions drive deploys:
  - **API** — Fastify 5 + oRPC on a Worker via `httpServerHandler`; `pluginTimeout: 0`; CPU limit raised to 5 min (`limits.cpu_ms`); `/healthz`, SSE and cookies unchanged.
  - **Product** — `@opennextjs/cloudflare` (Node runtime, no edge routes); R2 incremental cache; admin SSR role gate unchanged; custom domains via Wrangler routes.
  - **Landing** — static export to Workers Static Assets.
  - **Data** — Neon (serverless Postgres 17) behind a Hyperdrive binding, transaction pooling, dedicated Hyperdrive role with pooling disabled at Neon; Drizzle and the numbered DDL files unchanged; nightly encrypted `pg_dump` to R2 plus Neon PITR.
  - **Pipeline** — one Cloudflare Workflow instance per generation; stage = `step.do`; `generation_jobs` stays the durable truth and is written in the same transaction as instance creation; cancel = instance terminate + `canceling` flag; retries via Workflows step retries with the existing error classification; reaper/retention/snapshot-TTL on Cron Triggers (≤ 15 min CPU/wall).
  - **Blobs** — R2 bindings instead of the S3 client; local dev keeps MinIO behind a driver switch.
  - **CI/CD** — GitHub Actions with OIDC (actions pinned to SHAs): PR checks (turbo lint/typecheck/test/build + eval smoke) → `wrangler versions upload` preview on `*.workers.dev`; main auto-deploys: build → DDL applied to Neon first → staged rollout (`wrangler versions deploy`) with instant rollback via the previous version.
- **Consequences:** No servers to patch; scale-to-zero; one platform bill ($5/mo Workers Paid + Neon + R2 free tiers at launch). Accepted limits: 128 MB per isolate bounds large-repo ingest (pre-flight caps `MAX_REPO_FILES`/`MAX_REPO_BYTES` are the guard; a Cloudflare Container for ingest/index is the documented fallback if a golden repo overflows); 30 s default CPU per HTTP request (raised to 5 min for the API Worker); Neon dev tiers sleep and need warm-up. Docs that describe the running system (`docs/HOW_GENERATION_WORKS.md`, `docs/DEVELOPING.md`, `apps/api/CLAUDE.md`) still describe the current pg-boss code and are updated as part of implementing R9, not before.
- **Revisit when:** Isolate memory blocks golden-repo ingest even with caps → move ingest/index to a Cloudflare Container. Sustained Neon cost above a comparable VPS at real traffic. Workers runtime regressions in Fastify/OAuth/SSE compatibility that block a release → fall back to a Container hosting the API.
