# app/models/ — SQLAlchemy ORM

All models inherit `Base` from `app/db/session.py`. UUID PKs via
`server_default=text("gen_random_uuid()")` (requires pgcrypto/PG13+).

## Domain tables

| Model | Table | PK column | Notes |
|-------|-------|-----------|-------|
| `User` | `users` | `user_id` | email unique+indexed. `hashed_password` **nullable** — OAuth users never set one, and a dummy hash is indistinguishable from a real one. `is_active` for disable-without-cascade-delete. |
| `Repository` | `repositories` | `repo_id` | Unique on **(user_id, github_url)**. Was globally unique on `github_url`, so once one user added `facebook/react` nobody else ever could. |
| `Tutorial` | `tutorials` | `tutorial_id` | FK repo_id CASCADE. `generated_at` kept (domain meaning) plus `updated_at` for authoring edits. |
| `Module` | `modules` | `module_id` | ordered by `order_index`, which is **not** uniquely constrained per tutorial — nothing at the DB level stops two modules sharing a position, so writers must keep it a contiguous 0..n-1 sequence themselves (`services/author.py` resequences on delete and requires a full permutation on reorder). |
| `Quiz` | `quizzes` | | **`options` JSONB holds the answer key** — its dicts carry `is_correct`, and `correct_answer` is derived from it. Never serialise `options` raw; see `schemas/tutorial.py::QuizOption`. Nothing in the pipeline creates quizzes yet — only `routers/author.py` does. |
| `UserProgress` | `user_progress` | | Completion rows. `uq_user_module` makes check-then-insert a race — verified: 7 of 8 concurrent completions raised `IntegrityError`. Write with `ON CONFLICT`. |
| `UserSettings` | `user_settings` | | 1:1 with User. |
| `Notification` | `notifications` | | Produced only by the worker on generation finish (`services/notifications.py::notify_generation_finished`). The producer existed from the start but was **called from nowhere**, so the table stayed empty and the whole UI rendered blank — wired up in the notification slice. |

## Credentials (`credentials.py`)

`UserLLMCredential` — BYOK keys. **Highest-risk table in the product**: these bill the
*user's* account.

- `ciphertext` / `nonce` are `bytea`, AES-256-GCM. `key_version` from day one so rotating
  the KEK (or moving to KMS envelope encryption) is a migration, not a rewrite.
- `provider` / `label` / `last_four` are plaintext **so the settings UI never decrypts**.
- `base_url` supports any OpenAI-compatible endpoint (Ollama, LiteLLM, a gateway) — users
  bring their own URL as well as their own key.
- `last_validated_at` is a UI hint only. A key can be revoked upstream at any moment, so it
  is never an authorisation decision.

**⚠️ The credential must never enter orchestrator step context.**
`TutorialStepExecution.input_data`/`output_data` persist the whole accumulating dict to
Postgres verbatim. Steps get `user_id`; the AI client resolves the credential at call time
and never returns it.

## Billing (`billing.py`) — dormant

Schema only. Nothing reads or writes these in Phase 1 (docs/DECISIONS.md D7: BYOK free and
unlimited, 5 lifetime platform generations, no paid tier yet). They exist now because
adding billing tables later means migrating a table with real rows.

`CreditTransaction` is an **append-only ledger**; `UserCreditBalance` is a cache of its sum.
Never mutate a transaction row — write a compensating one. `idempotency_key` is uniquely
constrained so a redelivered Stripe webhook or a retried generation cannot double-charge.

## Orchestration tables (`orchestration.py`)

| Model | Purpose |
|-------|---------|
| `TutorialInstance` | One generation request. `status`: pending/running/completed/failed. |
| `TutorialExecution` | One attempt at an instance. Tracks `current_step_order`. |
| `TutorialStepExecution` | Per-step audit row: input_data, output_data, prompt_used, llm_response, error_message. |
| `TutorialStepConfig` | Per-step-type prompt/model/temperature config, unique on `step_type`. Rows auto-created with `prompt_template="Default prompt"` if absent (see `orchestrator/agent.py`). |

`TutorialInstance` links to `User` but **not** to `Repository` or `Tutorial` — it stores a
raw `repo_url` string. The join back to the produced tutorial is by URL matching, not FK.
Both sides are normalised through `repo_utils.normalise_repo_url`, which is the only reason
that match is reliable.

**⚠️ Alembic does not detect a changed `ondelete` rule either.** Same blind spot as CHECK
constraints — it compares FK columns, not their referential actions, so an autogenerated
migration comes out empty.

Both orchestration FKs shipped without `ondelete`, defaulting to NO ACTION. The ORM's
`cascade="all, delete-orphan"` hid it, because that only applies when SQLAlchemy walks the
relationship: deleting a **user** cascades to `tutorial_instances` in the database, which
never loads the execution rows, so Postgres aborted the transaction. Account deletion failed
for every user who had ever started a generation. Fixed in `a5b0a1b30fd5`. Audit with:

```sql
select tc.table_name, kcu.column_name, rc.delete_rule
from information_schema.table_constraints tc
join information_schema.key_column_usage kcu on kcu.constraint_name = tc.constraint_name
join information_schema.referential_constraints rc on rc.constraint_name = tc.constraint_name
where tc.constraint_type = 'FOREIGN KEY' and tc.table_schema = 'public';
```

## Enums (`enums.py`)

`StrEnum` members, **all lowercase**. `RepositoryStatus`, `RunStatus` (shared by all three
orchestration tables), `TutorialLevel`, `QuestionType`, `NotificationType`,
`TutorialVisibility`.

Because they're `StrEnum`, `repo.status == "completed"` still works and f-strings render
the value — so existing comparison code was unaffected by the conversion.

Columns are built with `enum_column()`, which sets `native_enum=False` (VARCHAR + CHECK,
not a Postgres `ENUM` type). Native enums can't drop a value and `ALTER TYPE ADD VALUE`
can't run in a transaction, which would make every future status change an out-of-band
migration.

**⚠️ Alembic does not autogenerate CHECK constraints.** `alter_column` with a non-native
`Enum` widens the VARCHAR and stops — verified on a scratch DB, which came out with *zero*
CHECK constraints and accepted `'BANANA'` as a repository status. When you add or change an
enum column, **write the `op.create_check_constraint` by hand** and confirm with:

```sql
select conrelid::regclass, conname from pg_constraint
where contype='c' and connamespace='public'::regnamespace;
```

Migrations hardcode enum values as literals rather than importing `app.models.enums` — a
migration describes one historical transition and must not change meaning when a model is
edited later.

## Search indexes (`pg_trgm`)

`services/search.py` filters with `ILIKE '%term%'`. A leading wildcard makes a B-tree
useless, so migration `80e2e03a0776` installs `pg_trgm` and adds **GIN trigram** indexes on
`repositories.name`, `tutorials.title`, `modules.title`, `modules.content_markdown` and
`quizzes.question_text`.

They are declared on the models (`postgresql_using="gin"`,
`postgresql_ops={"col": "gin_trgm_ops"}`) **as well as** in the migration. Both are required:
without the model declaration `alembic check` reads the DB index as drift and autogenerate
offers to drop it; and alembic renders a GIN/opclass index as a plain `create_index` that
silently omits `gin_trgm_ops`, producing an index the planner cannot use for ILIKE — which is
why that migration is hand-written.

## Timestamps (`mixins.py`)

`TimestampMixin` gives `created_at`/`updated_at`, both server-side defaults so rows written
by migrations or raw SQL are still correct. Applied to `User`, `Repository`, `Module`,
`Quiz`, `UserSettings`, `TutorialInstance`.

Not applied where a domain-specific timestamp already means something: `Tutorial`
(`generated_at`), `UserProgress` (`completed_at`), `TutorialExecution`
(`started_at`/`completed_at`), `Notification` (`created_at`/`read_at`).

## Cross-cutting gaps

- No tenant/organization table. Everything is scoped to a single `user_id`.
- `TutorialStepExecution.input_data`/`output_data` are unbounded JSON holding full LLM
  context — this table will dominate DB size.
- **No migrations.** Changing a column here has no path to production. See root `CLAUDE.md`.
